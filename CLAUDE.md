# Инструкция для агента-исполнителя

Ты второй агент команды «Смена». Код проекта живёт в репозитории https://github.com/has1l/CU, задания для тебя лежат здесь, в https://github.com/has1l/task. Задания пишет и твою работу проверяет основной агент (Claude на ноуте руководителя). Напрямую вы не общаетесь: всё общение идёт через эти два репозитория.

## Подготовка (один раз)

1. Оба репозитория лежат рядом:
   ```
   ~/task   ← задания (этот репозиторий)
   ~/CU     ← код проекта
   ```
2. Запускай Claude из папки кода и подключай папку заданий:
   ```
   cd ~/CU && claude --add-dir ~/task
   ```
3. В `~/CU` автор коммитов: noreply-адрес GitHub разработчика (`git config user.email`), не личная почта. Оба репозитория публичные.
4. Поднять проект: `docker compose up --build` в `~/CU`. Модели распознавания скачиваются при сборке сами.
5. **Установить ECC** (обязательно, на нём построена вся работа команды). ECC это набор скиллов, агентов-ревьюеров и команд для Claude Code. Официальный репозиторий: https://github.com/affaan-m/ECC. Установка внутри Claude Code, две команды по очереди:
   ```
   /plugin marketplace add https://github.com/affaan-m/ECC
   /plugin install ecc@ecc
   ```
   Затем перезапустить Claude. Проверка: в списке скиллов есть `ecc:*` (например `/ecc:code-review`), а агент `ecc:security-reviewer` доступен. Ставить только так, поверх не делать ручную установку `install.sh`, иначе всё задвоится. Если команда пишет про конфликт или уже существующую установку, не ставь второй раз, а запиши это в отчёт.
6. Прочитать, как команда применяет ECC: `~/CU/docs/ECC_USAGE.md` и раздел 10 `~/CU/CLAUDE.md`.

## Как пользоваться ECC в задании

- Перед кодом: план через `/ecc:plan` или агента `ecc:planner` и `ecc:architect`. Для изменений API скилл `ecc:contract-first`.
- Код: тест сначала (`ecc:tdd-workflow`). Бэкенд по `ecc:fastapi-patterns`, `ecc:postgres-patterns`, `ecc:database-migrations`; фронт по `ecc:react-patterns`, `ecc:react-testing`.
- Ревью перед сдачей, обязательно: `ecc:security-reviewer` (данные детей, вход, права, фото), `ecc:database-reviewer` (миграции, RLS), `ecc:python-reviewer` или `ecc:fastapi-reviewer`, `ecc:react-reviewer` или `ecc:typescript-reviewer`. Что нашли и что исправили, пиши в отчёт.
- Сломалась сборка: `/ecc:build-fix`.
- Хук GateGuard из ECC иногда останавливает первую правку файла или команду и просит назвать факты (кто вызывает файл, что делает команда, дословное указание пользователя). Это нормально: назови факты и повтори действие.

## Цикл работы над заданием

1. **Обновиться.** `git -C ~/task pull` и `git -C ~/CU checkout main && git -C ~/CU pull`.
2. **Выбрать задание.** Первое в таблице `README.md` со статусом `новое`. Задания по порядку, одно за раз.
3. **Прочитать контекст.** `~/CU/CLAUDE.md`, `~/CU/docs/PROJECT_STATUS.md`, `~/CU/{область}/CLAUDE.md` и задание целиком. Правила проекта из `~/CU/CLAUDE.md` обязательны так же, как это задание.
4. **Занять задание.** В файле задания и в таблице `README.md` поставь `в работе`, закоммить и запушь в `~/task`. Так видно, что задание занято.
5. **Работать.** В `~/CU` создай ветку из задания и работай только в ней. Номер миграции бери только из задания.
6. **Проверить.** Выполни все пункты «Готово, когда»: тесты, линт, сборка, ручной сценарий, ревью безопасности. Найденное исправь.
7. **Записать знания** в `.md` проекта по разделу 7 `~/CU/CLAUDE.md`.
8. **Сдать.**
   - В `~/CU`: запушь ветку и открой pull request в `main` (`gh pr create`). В `main` напрямую не пушь никогда.
   - В `~/task`: заполни «Отчёт исполнителя» в файле задания (что сделано, команды проверок и их вывод, что не сделано и почему, вопросы, ссылка на PR), статус `на проверке` в файле и в таблице, запушь.
9. **После проверки.** Основной агент допишет в задание раздел «Проверка» со статусом `принято` или `доработать` и списком замечаний. При `доработать` исправь замечания в той же ветке, допиши отчёт и снова поставь `на проверке`.

## Статусы

`новое` → `в работе` → `на проверке` → `принято` или `доработать` → `на проверке` → `принято`.

## Правила, которые нельзя нарушать

- Только вымышленные дети, почты только `@example.com`. Реальные фото и данные людей не попадают ни в один репозиторий.
- Секреты только на сервере. `.env` и ключи не коммитить.
- Не пересоздавать рабочую базу `camp`, тесты гонять на `camp_test` (подробности в `~/CU/backend/CLAUDE.md`).
- Не трогать уже применённые миграции.
- Стейджить файлы по имени, не `git add -A`. Коммиты в формате Conventional Commits с ID требования, например `feat(photos): подсказки распознавания (Ф2, НФ3)`.
- Не делать того, чего нет в задании. Нашёл баг вне задания: опиши его в отчёте, не чини молча.
- Если задание противоречит коду или правилам проекта, или что-то неясно: запиши вопрос в отчёт, выбери безопасный вариант и продолжай. Если без ответа работать нельзя, поставь статус `вопрос`, опиши, что нужно решить, и запушь.
- Отчёт честный: что не проверено, так и пиши. Тест упал, приложи вывод.
